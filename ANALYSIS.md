# Разбор идеи и план реализации

Документ отвечает на пункты 1–4 раздела «Задача для AI-агента» из `IDEA.md`.
Пункт 5 (прототип) выполнен: рабочий код лежит в `src/astrocal`, результат —
в `out/`.

## 1. Что здесь на самом деле за задача

Идея выглядит как «сгенерировать текст для Телеграма», но по сути это
**ETL-конвейер над астрономическими данными** с ручным контролем качества на
выходе. Текст — это 5% работы; 95% — получить проверенные числа.

Задача разбивается на четыре независимых слоя, и это главное архитектурное
наблюдение:

| слой | чем считается | воспроизводимость |
|---|---|---|
| Солнце, Луна, планеты | эфемериды DE440 + Skyfield | 100% детерминированно |
| спутники планет, кометы, каталоги | JPL satellite BSP / Horizons, MPC, HIP, OpenNGC | детерминированно при фиксированных данных |
| метеорные потоки | таблица λ☉ от IMO + расчёт момента | почти детерминированно |
| космонавтика и пролёты МКС | расписания Роскосмоса/NASA, TLE | **не воспроизводится**, стареет за дни |

Отсюда следует главный вывод для архитектуры: **последний слой обязан быть
отделён от остальных и иметь собственный статус проверки.** Смешивать
«новолуние 11 сентября 06:00» (точность секунды на сто лет вперёд) и
«стыковка Прогресса 11 сентября 21:36» (догадка) в одном списке без пометок —
это и есть тот дефект исходного календаря, ради которого всё затевалось.

## 2. Уточняющие вопросы

Работу они не блокируют — по каждому принято решение по умолчанию, но ответы
изменят настройки:

1. **Порог интересности.** Сколько строк должно быть в посте? Сейчас за сентябрь
   получается 39. Можно сделать 25 (только яркое) или 60 (всё подряд).
   *По умолчанию:* сближения комет публикуются, только если объект ярче +6.5m и
   расстояние меньше 0.5° (или звезда ярче +4.5m в пределах 1°).
2. **Чья точка наблюдения.** Все фильтры видимости сейчас считаются для Москвы.
   Для канала на всю страну логичнее считать «видно хотя бы из одного крупного
   города РФ». *По умолчанию:* Москва.
3. **Что делать с неподтверждённой космонавтикой.** Сейчас такие строки в пост
   не идут вообще. Альтернатива — публиковать с пометкой «предварительно».
   *По умолчанию:* не публиковать.
4. **Источник блеска комет.** MPC-параметры систематически расходятся с
   реальными наблюдениями (см. 161P: MPC ~13m, COBS-оценки у AstroAlert ~10.6m).
   Подключать ли COBS/vanbuitenen как третий источник?
   *По умолчанию:* MPC + Horizons, обе оценки в протоколе.
5. **Периодичность.** Разовый запуск раз в месяц руками или cron + автопубликация
   в канал? От этого зависит, нужен ли слой публикации.

## 3. Три варианта реализации

### Вариант A — «расчётное ядро + ручная вычитка» (реализован)

Python-пакет считает всё, что считается, отдаёт два файла: готовый пост и
протокол проверки. Космонавтика приходит из JSON-файла, который человек
заполняет и проверяет руками. Человек читает протокол и решает, что публиковать.

- **Плюсы:** ошибок вида «Уран стоит 8-го вместо 10-го» не бывает в принципе;
  каждая цифра прослеживается до источника; работает офлайн (кроме Horizons и TLE).
- **Минусы:** нужен человек на 20–30 минут в месяц.
- **Когда брать:** это MVP и, скорее всего, окончательный вариант.

### Вариант B — A + автоматический сбор космонавтики

Добавляется парсер расписаний (Launch Library 2 API, NextSpaceflight, RSS
Роскосмоса) и агрегатор новостей. JSON космонавтики заполняется сам, человек
только подтверждает.

- **Плюсы:** снимает ручной труд там, где его больше всего; Launch Library 2
  даёт статус пуска (`GO` / `TBD` / `Hold`), а это ровно то, чего не хватает.
- **Минусы:** сторонние API падают и меняются; для стыковок/расстыковок
  структурированного источника вообще нет — их приходится тянуть из текста
  новостей, а это уже LLM-извлечение с риском галлюцинаций.
- **Когда брать:** если календарь делается регулярно и ручная часть надоела.

### Вариант C — A + LLM-редактор и автопубликация

Поверх варианта A ставится дешёвая модель (DeepSeek), которая причёсывает
формулировки, отбрасывает скучное и укладывает пост в нужный объём, плюс
публикация в канал по расписанию.

- **Плюсы:** полностью автономно.
- **Минусы:** LLM в конвейере точных чисел — источник тихих ошибок: перепутает
  «севернее» и «южнее», округлит 0°25′ до 0.5°, поменяет знак фазы. Ради стиля
  ставить под удар главное свойство продукта не стоит.
- **Когда брать:** только если модель работает **строго с текстом** и ей
  запрещено трогать числа (шаблоны + валидация регулярками на выходе).

**Рекомендация:** A сейчас, B — вторым шагом. C не брать: выигрыш косметический,
риск содержательный.

## 4. Стек

- **Python 3.12**, `skyfield` — эфемериды, видимые координаты, альманах фаз и
  сезонов, SGP4 для МКС.
- **JPL DE440s** (33 МБ, 1849–2150) — Солнце, Луна, планеты.
- **JPL jup380s.bsp** (51 МБ, 2015–2030) — Ио, Европа, Ганимед, Каллисто.
  Полное ядро `jup365.bsp` весит 1 ГБ и здесь не нужно.
- **JPL Horizons API** — Титан (компактного BSP с крупными спутниками Сатурна
  не существует: `sat441l` — 608 МБ) и, главное, **независимая сверка** всех
  ключевых расчётов.
- **MPC CometEls.txt** — орбитальные элементы комет.
- **Hipparcos** (41 411 звёзд ярче 8m) и **OpenNGC** (1 767 объектов ярче 12m) —
  каталоги для кросс-матча.
- **Celestrak TLE** — пролёты МКС.
- `numpy` / `pandas` — векторные расчёты по сетке времени.

Всё, кроме Horizons и TLE, кэшируется в `data/`, так что повторный прогон
не требует сети.

## 5. Риски

| риск | последствие | что сделано |
|---|---|---|
| Блеск комет по MPC систематически неверен | публикуем «яркую комету», которую никто не увидит | считаем по MPC **и** по Horizons, обе цифры в протоколе; на 161P расхождение с исходником зафиксировано |
| Расписания пусков переносятся | в календаре событие, которого не будет | космонавтика вынесена в JSON с флагом `include` и обязательным источником; неподтверждённое не публикуется |
| TLE МКС стареет | время пролёта уходит на минуты, дата серии — на сутки | уверенность события падает при прогнозе дальше 10 суток от эпохи TLE, в протоколе указан возраст элементов |
| Геоцентрика vs топоцентрика | расхождение до 1° для Луны — как раз масштаб публикуемых величин | в посте геоцентрические расстояния (как в печатных календарях), топоцентрика — только для покрытий и видимости; в протоколе указано, что именно считалось |
| Один момент сближения превращается в 20 строк | нечитаемый пост | поиск локальных минимумов + дедупликация в окне 12 часов |
| Момент минимума приходится на день или на время под горизонтом | формально верная, но бесполезная строка | событие сдвигается к ближайшему наблюдаемому моменту, в протоколе указаны оба времени |
| OpenNGC/Hipparcos меняются | нестабильный результат между прогонами | файлы кэшируются локально, версия фиксируется вместе с выдачей |
| Horizons недоступен | нет второго источника | сверка опциональна (`--no-horizons`), падение модуля Титана не роняет сборку |

| Подключение OccultWatcher Cloud как основной ленты покрытий | у сервиса нет открытого API без авторизации, страницы отдаются как SPA; сейчас используется годовой файл IOTA с asteroidoccultation.com и собственный пересчёт полосы | 1 день при наличии доступа |

| Точная граница полосы покрытия (сейчас сетка 2°) | для формулировки «видно на Юге ЕЧР» этого хватает; для карты нужна сетка 0,25° и построение контура | 1 день |
| Автосбор стыковок и расстыковок | структурированного источника не существует, только новости — это LLM-извлечение с риском галлюцинаций в числах | 1–2 дня, с оговорками |
| Cron и автопубликация без человека | сознательное решение: строки с уверенностью «средняя» и «низкая» должен смотреть человек | 0,5 дня, если всё же нужно |

Календарь на конкретный месяц силами написанного кода делается за
**20–30 минут**: сборка 3–5 минут машинного времени, остальное — вычитка
протокола и заполнение космонавтики.

## 8. Как считается каждая категория

| категория | метод | второй источник |
|---|---|---|
| фазы, перигей/апогей, равноденствия | `skyfield.almanac` по DE440s | JPL Horizons (координаты в момент события) |
| сближения Луны с планетами и звёздами | минимум геоцентрического расстояния | Horizons |
| покрытия планет и звёзд Луной | геометрия на сетке ITRS 2° по всей Земле | Horizons (расстояние в момент максимума) |
| затмения Солнца | та же геометрия: полосы полной и частной фазы; максимум — минимум расстояния от центра Земли до оси тени | момент сверяется с публикуемым временем наибольшего затмения |
| затмения Луны | `skyfield.eclipselib` + радиусы тени с поправкой Данжона | — |
| стояния, противостояния, соединения | нули и переходы разности эклиптических долгот | Horizons (выборка Δλ с шагом 2 ч) |
| видимость планет | arcus visionis по блеску + высота в момент нужного погружения Солнца | — (критерий явно указан в протоколе) |
| галилеевы спутники | jup380s.bsp, смещение по ΔRA·cos δ | — |
| Титан | Horizons (компактного BSP с крупными спутниками Сатурна нет) | — |
| метеорные потоки | момент, когда λ☉ (J2000) равна табличной | таблица IMO |
| кометы | элементы MPC → трек 15 мин → кросс-матч с HIP и OpenNGC | Horizons T-mag и координаты |
| яркие астероиды | эфемериды Horizons + тот же кросс-матч | — |
| сближения NEO | CNEOS Close Approach API | — |
| пуски | Launch Library 2 (статус Go/TBD) + ручное подтверждение | новости, Википедия |
| пролёты МКС и ККС | Celestrak TLE + SGP4 | — (уверенность падает с возрастом TLE) |

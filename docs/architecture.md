# Архитектура AstroCalendar Studio

Документ для тех, кто будет менять код. Продуктовое описание — в
[README](../README.md).

## Слои и границы

```
              PySide6 GUI (src/astrocal_studio)
   таблица · редактор · предпросмотр · QA · LIVE · guide
                          │  только вызовы сервиса
              Прикладной слой (src/astrocal_app)
  Issue · EditableEvent · workspace · datastatus · live · livefeed
                          │  только вызовы ядра
                  Ядро (src/astrocal)
     events/* · observing · telegram · qa · rating · verify
                    │            │             │
        JPL · MPC · IOTA      live/*        render/*
        TNS · CNEOS · SBDB    состояние      matplotlib
        Horizons · Celestrak  и снимки       → PNG
                    │
              net.py · secrets.py
```

Правила, которые не стоит нарушать:

1. **В интерфейсе нет астрономии.** Ни одной формулы, ни одного обращения к
   Skyfield. Если виджету что-то нужно посчитать — это метод сервиса.
2. **Ядро не знает про Qt.** `astrocal` импортируется в тестах и CLI без
   установленного PySide6.
3. **Рендеринг отделён от интерфейса.** `astrocal/render` принимает время,
   место и объект, возвращает путь к PNG. Виджет только показывает картинку.
4. **Долгие операции — в поток.** Всё, что дольше ста миллисекунд, уходит в
   `TaskRunner` (`astrocal_studio/workers.py`).

## Ключевые типы

| тип | где | зачем |
|---|---|---|
| `Event` | `astrocal/core.py` | результат расчёта: время, текст, источники, флаги |
| `EditableEvent` | `astrocal_app/models.py` | событие плюс решения редактора |
| `Issue` | `astrocal_app/models.py` | выпуск месяца: события, фильтры, порядок |
| `Publication` | `astrocal/telegram.py` | пост, разбитый по лимиту Telegram |
| `Circumstances` | `astrocal/observing.py` | обстоятельства наблюдения в городе |
| `Pass` | `astrocal/render/satellite_map.py` | один видимый пролёт станции |
| `Candidate` | `astrocal/occultation_feeds.py` | кандидат в покрытие звезды астероидом |
| `Occultation` | `astrocal/events/asteroid_occultations.py` | покрытие целиком: полоса, границы, свежесть прогноза |

| `FeedNeo` | `astrocal/neo_feeds.py` | строка таблицы блеска NEO, второй источник |
| `ScheduledEvent` | `astrocal/live/model.py` | прогнозируемое событие живой ленты |
| `DiscoveryEvent` | `astrocal/live/model.py` | открытие: комета, новая, сверхновая |
| `LiveUpdate` | `astrocal/live/model.py` | уточнение известного прогноза |
| `LiveState` / `Snapshot` | `astrocal/live/state.py` | память ленты между запусками |

## Идентичность события

`Event.event_id` — sha1 от категории, даты и текста без чисел. Смысл: время
события может сдвинуться на час, а блеск — на десятую величины, но это то же
самое событие, и редакторская правка должна за ним последовать.

`Event.fingerprint()` — sha1 от точного времени и полного текста. Меняется при
любом уточнении расчёта; по нему `workspace` понимает, что данные события
изменились после сохранения, и предупреждает редактора.

## Как добавить новый тип событий

1. Модуль в `astrocal/events/` с функцией `all_events(start, end) -> list[Event]`.
2. Вызов в `astrocal/build.py::collect` — обязательно внутри `try`, чтобы отказ
   внешнего источника не ронял весь расчёт.
3. Правило классификации в `astrocal/taxonomy.py::classify` и запись в `KINDS`
   — иначе событие попадёт в «Прочее» и не получит галочки в интерфейсе.
4. Правило ранга в `astrocal/rating.py::rank_event`.
5. При необходимости — ветка в `astrocal/render/event_map.py::for_event`.
6. Тесты: значение против внешнего источника в `tests/test_astronomy.py`,
   классификация в `tests/test_editor.py`.

Интерфейс менять не нужно: категории, фильтры и таблица строятся из таксономии.

## Потоки и отзывчивость

`TaskRunner` — обёртка над `QThreadPool`. Функция получает именованный аргумент
`progress(stage, percent)`, если объявляет его в сигнатуре; про Qt она при этом
ничего не знает и одинаково работает из CLI.

Ошибка фонового задания не роняет приложение: пользователь видит диалог с
коротким сообщением, полный traceback — в разворачиваемой части.

## Данные и кэш

Всё сетевое кэшируется в `data/cache/`. Панель «Данные» показывает возраст
каждого источника и позволяет обновить точечно.

Первичная загрузка — `astrocal_app/bootstrap.py`. Там перечислено всё, что
приложение умеет скачать само: эфемериды, каталоги звёзд и туманностей, линии
созвездий, элементы комет (обязательное) и ленты предсказаний покрытий с
ядрами ориентации Луны (необязательное). Загрузка потоковая, файл пишется во
временный `.part` и переименовывается только после успеха — оборванная закачка
не оставляет битую эфемериду, на которой расчёт упадёт в середине.

Главное окно проверяет наличие данных при старте и предлагает скачать; кнопка
дублируется на вкладке «Данные» и в меню «Файл». Расчёт без обязательных
файлов не запускается — вместо непонятной ошибки показывается предложение
скачать.

Где искать данные, решает `astrocal/config.py::_root()`:

* переменная окружения `ASTROCAL_HOME`, если задана;
* каталог рядом с exe для замороженной сборки (`sys.frozen`);
* корень репозитория при запуске из исходников.

Это важно именно для сборки: внутри дистрибутива PyInstaller `__file__`
указывает в `_internal`, куда нельзя писать и где данных нет.

## Живая лента

Календарь считает будущее, лента сравнивает состояния. Разница принципиальная,
и из неё следует всё устройство `astrocal/live`.

**Снимок источника** (`Snapshot`) — множество идентификаторов, отданных в
прошлый раз, в файле `data/live/<источник>_state.json`. Открытия — это разница
между текущим списком и снимком. Отдельно обрабатывается первый запуск: снимка
нет, и объявлять открытием весь каталог TNS или MPC нельзя, поэтому снимок
просто записывается, а лента остаётся пустой.

**Состояние записей** (`LiveState`, `data/live/state.json`) хранит для каждой
записи `first_seen_at`, `last_seen_at`, `last_updated_at`, `read`, `ignored`,
`added_to_workspace` и хэши содержательных полей. Отсюда берутся статусы
`NEW` / `UPDATED` / `UNCHANGED` и счётчик непросмотренного на вкладке.

Поле `retain` у записи перечисляет ключи `payload`, которые нужно помнить между
запусками. Через него наблюдатель за покрытиями получает прежнюю центральную
линию и считает сдвиг полосы. `prepare()` читает прошлое состояние, ничего не
меняя, — сравнение должно произойти до записи нового.

**Семантика.** `ScheduledEvent` можно поставить в месячный выпуск:
у него есть момент наступления, и он был предсказуем. `DiscoveryEvent` — нет:
открытие происходит тогда, когда происходит, и задним числом в календарь не
вставляется. `LiveUpdate` ссылается на исходную запись через `target_id`.

**Перенос в выпуск** идёт через `service.add_live_event`: событие получает
`provenance["origin"] = "live"`, ссылку на исходную запись и хэш данных.
По расхождению хэша `livefeed.Feed.source_changes` находит события, у которых
источник изменился после переноса. `apply_source_update` обновляет расчётную
часть и **никогда** не трогает `editor_text`.

## Как добавить источник в ленту

1. Модуль в `astrocal/live/` с функцией
   `check(...) -> tuple[list[LiveRecord], dict]`. Сводка обязана содержать
   `status`; ошибку источника возвращают в ней, а не бросают наверх.
2. Регистрация в `discovery_service.KINDS` и `TITLES`.
3. Проверки в `astrocal/qa_live.py::CHECKS`.
4. Строка в `astrocal_app/datastatus.py::sources`, чтобы был виден возраст.
5. Флажок в `astrocal_studio/widgets/live_panel.py::KIND_FILTERS`.
6. Тесты со заглушкой сети: снимок, повторный запуск, пороги значимости.

## Второй источник блеска NEO

`astrocal/neo_feeds.py` разбирает две таблицы с astro.vanbuitenen.nl. Разбор
сделан на штатном `html.parser`, а не на pandas с lxml: разметка простая, а
лишняя зависимость в сборке ни к чему.

Две особенности, ради которых код выглядит именно так. На странице ярких
объектов строки `<tr>` не закрыты — новый `<tr>` начинается сразу после
последней ячейки предыдущего, и разбор «по закрывающему тегу» молча возвращал
ноль строк. Поэтому новая строка закрывает предыдущую явно. И заголовок
колонки `H` содержит подстрочный знак, который на сайте менялся, — имена
колонок сравниваются по латинице и цифрам, всё остальное отбрасывается.

Набор колонок проверяется при каждом разборе: если структура таблицы
изменится, будет явная ошибка, а не молча разъехавшиеся значения.

## Сеть и ключи

Все внешние запросы идут через `astrocal/net.py`: кэш на диске с явным сроком
годности, пауза между обращениями к одному хосту, выдержка при 429 и 5xx,
подстановка просроченного кэша, если свежих данных получить не удалось.
Прямой `requests.get` в новом коде — ошибка ревью.

Ключи читаются `astrocal/secrets.py` из `.env`. `MissingCredentials` — это не
сбой, а сообщение: источник не опрашивается, остальные работают. Ключ не
должен попасть ни в `provenance`, ни в QA-отчёт, ни в текст ошибки.

## Встроенная справка

Текст руководства лежит в `astrocal_studio/guide.py` — в коде, а не файлом
рядом с программой: собранное приложение должно открывать справку без `docs/`
и без интернета. `docs/guide.md` генерируется оттуда же
(`python -m astrocal_studio.guide`), чтобы два текста не разошлись.

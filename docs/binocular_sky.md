# Binocular Sky

Персональный планетарий для наблюдений в бинокль с конкретной точки на земле.

## Зачем это

Обычный планетарий отвечает на вопрос «где сейчас M31». Наблюдателю нужен
другой ответ:

> M31 станет видна с вашей точки в 22:47, выйдя из-за правого края крыши.
> Высота 18°. В вашем 10×50 это отличный объект.

Разница в трёх вещах, которых в обычном планетарии нет:

* **конкретный прибор** — 10×50 и 15×70 показывают разное, и рейтинг объекта
  считается под ту оптику, что у вас в руках;
* **реальный участок** — дом, деревья и забор поднимают горизонт до двадцати
  градусов, и объект бывает «взошёл, но не виден» ещё час;
* **готовая программа на ночь** — не каталог, а список из десятка целей,
  отсортированный по тому, ради чего стоит выйти во двор.

## Запуск

```
cd idea-astrocalendar-month
python -m binocular_sky
```

Сквозная проверка всего сценария (считает ночь, строит поле бинокля, сохраняет
снимки сцены в `out/`):

```
python scripts/smoke_binocular_sky.py
```

Тесты:

```
python -m pytest tests/test_binocular_sky.py -q
```

## Архитектура

Binocular Sky не содержит собственной астрономии. Расчёты берутся из ядра
`astrocal` — того же, на котором работает AstroCalendar Studio:

```
                        astrocal
              (Skyfield, DE440s, jup380s,
               Hipparcos, OpenNGC, поиск корней)
                     ↙              ↘
      AstroCalendar Studio        Binocular Sky
        календарь и лента          наблюдатель у дома
```

Внутри самого приложения слои разделены жёстко:

```
src/binocular_sky/
    app.py, __main__.py      запуск
    main_window.py           окно: состояние и раскладка панелей
    storage.py               профили в %APPDATA%\BinocularSky
    workers.py               фоновые расчёты
    theme.py                 обычный и ночной вид

    models/     observer.py    площадка: GPS, высота глаз, пояс, Бортль
                binocular.py   оптика и модель предельной величины
                scene.py       дом, деревья, забор, привязка фотографий
                horizon.py     маска местного горизонта
                target.py      цель наблюдения (одна модель для всех типов)

    services/   astronomy_service.py       координаты, ночь, Луна
                catalog_service.py         каталог целей и поиск по алиасам
                horizon_service.py         видимость и моменты появления
                recommendation_service.py  бинокулярный рейтинг
                scene_service.py           JSON для 3D и поле бинокля
                observing_service.py       план наблюдений

    widgets/    панели PySide6
    web/        сцена на Three.js (локально, без CDN)
```

Граница Python ↔ JavaScript проведена по одному правилу: **вся астрономия
остаётся в Python**. В сцену уходит готовый снимок — азимут, высота, блеск:

```
Python (Skyfield)  →  JSON  →  QWebChannel  →  Three.js
```

Снимок пересчитывается при смене времени, площадки, прибора или цели, а не
каждый кадр. За кадр JavaScript двигает только камеру.

## Офлайн

Приложение рассчитано на дачу с плохой связью:

* three.js лежит в `src/binocular_sky/web/vendor/` (MIT, версия r169), CDN не
  используется;
* мост `qwebchannel.js` берётся из ресурсов самого Qt;
* эфемериды и каталоги — файлы в `data/`, скачиваются один раз;
* Chromium запускается с отключёнными фоновыми сетевыми службами.

## Профиль наблюдателя

`ObserverProfile`: название, широта, долгота, высота над уровнем моря, высота
глаз, часовой пояс, класс неба по шкале Бортля.

Высота глаз хранится отдельно от высоты площадки не случайно: на небесные
координаты она не влияет, но именно она решает, видно ли поверх забора.

Координаты можно вставить строкой прямо из карт («55.324769, 38.349526»).
Площадок может быть несколько; у каждой свой участок.

## Профиль прибора

`BinocularProfile`: увеличение, апертура, истинное поле зрения, ориентация
изображения, необязательный ручной предел блеска. Выходной зрачок и видимое
поле вычисляются.

### Модель предельной звёздной величины

Это **оценка, а не гарантия**. Складывается из четырёх слагаемых:

1. **Небо.** Предел невооружённого глаза по классу Бортля: 1 → 7.8m,
   4 → 6.5m, 9 → 3.8m.
2. **Апертура.** `5·lg(D_эфф / D_зрачка)`, где `D_зрачка = 6 мм`.
   Эффективная апертура ограничена: если выходной зрачок больше зрачка глаза,
   лишний свет упирается в радужку — 7×50 в городе работает как 7×42.
3. **Увеличение.** `1.4·lg(Γ)`: увеличение растягивает фон неба, а звезда
   остаётся точкой, и контраст растёт.
4. **Высота и Луна.** Поглощение `0.28·(X − 1)` по воздушной массе (формула
   Пиквертона–Пёрселла) и отдельный штраф за лунную засветку.

Для 10×50 при Bortle 4 на высоте 45° получается около +12m.

Ручное значение перекрывает пункты 1–3, но высота и Луна вычитаются и из него.

## Местный горизонт и препятствия

Типы препятствий: `HOUSE`, `TREE`, `TREE_LINE`, `FENCE`, `CUSTOM_HORIZON`.

Каждое умеет отдать **силуэт** — точки (азимут, высота) с точки зрения глаз.
Из силуэтов собирается `HorizonProfile`: азимут → минимальная видимая высота,
на сетке 0.5° с интерполяцией по кругу.

Дом строится из примитивов: коробка стен плюс двускатная крыша. Blender не
нужен. Важная деталь: силуэт считается **по граням, а не по рёбрам**. Если
брать только рёбра, между коньком и карнизом остаются пустые ячейки сетки, и
сквозь «дыры» в крыше просвечивают планеты — на это есть отдельный тест.

Геометрия для расчёта и геометрия для 3D строятся из одних и тех же чисел,
поэтому дом на экране и дом в ответе «виден / закрыт» — один и тот же дом.

### Когда объект появится из-за дома

Момент ищется как корень

```
f(t) = высота_объекта(t) − горизонт_участка(азимут_объекта(t))
```

Обе части меняются: объект движется и по высоте, и по азимуту, а маска на новом
азимуте другая. Смена знака ищется на сетке в 2 минуты и уточняется бисекцией
до долей секунды.

Именно поэтому наблюдательный восход отличается от астрономического — иногда
на час.

## Бинокулярный рейтинг

`BinocularScore`, 0–100. Слагаемые:

| составляющая | вклад | что учитывает |
|---|---|---|
| доступность прибору | 0–35 | блеск против предела; для протяжённых — ещё и поверхностная яркость против фона неба |
| высота над местным горизонтом | 0–20 | у крыши смотреть нечего |
| вписывание в поле | 0–15 | помещается ли объект целиком; не выглядит ли точкой |
| помеха от Луны | 0–15 | фаза × близость × чувствительность типа |
| длительность окна | 0–10 | меньше получаса — не успеть |
| поправка по типу | −10…+8 | правила ниже |

Поправки по типу существуют потому, что M31 и Юпитер нельзя оценивать одной
формулой:

* Луна и яркие планеты почти нечувствительны к засветке; галактики и диффузные
  туманности — полностью;
* рассеянные скопления и астеризмы разрешаются на отдельные звёзды, поэтому
  поверхностная яркость к ним не применяется;
* планета получает премию, только если её диск различим: `размер × увеличение`
  против разрешения глаза. Уран в 10×50 — точка, и рейтинг это знает;
* двойная звезда оценивается по тому, разделит ли её прибор, и премия растёт
  плавно: пара, разделяемая впритык, и пара с запасом — разные вещи;
* галилеевы спутники имеют смысл, только когда виден сам Юпитер.

Пороги звёзд откалиброваны по фактическому распределению: за ночь для 10×50 при
Bortle 4 набирается около четырёхсот доступных объектов, медиана 54, 95-й
процентиль 87. Пять звёзд начинаются с 88 — это единицы процентов, то есть
«выйти ради этого стоит», а не «объект над горизонтом».

Объяснение «почему это интересно» собирается из тех же рассчитанных величин по
шаблонам. Никакой языковой модели: текст обязан следовать из чисел.

## Вид в бинокль

Круглое поле, масштаб которого задаётся полем зрения прибора и ничем больше.
Если поле 6.5°, а Каскад Кембла занимает 2.5°, он займёт примерно 38 % диаметра
круга. Масштабирование «чтобы было видно» здесь запрещено — весь смысл режима в
том, чтобы человек заранее понял, что увидит.

Смещения объектов от центра поля считает Python (гномоническая проекция);
JavaScript только умножает их на «пикселей на градус». Точки дальше 90° от
центра отбрасываются: без этой отсечки проекция заворачивала в поле объекты с
противоположной стороны неба.

Ориентация изображения сейчас `NORMAL`. Модель подготовлена под `INVERTED` и
`MIRROR` — они понадобятся, когда появится телескоп с диагональю.

## Ночной режим

Чёрный фон, только тусклый красный, никаких белых элементов; сама сцена
приглушается фильтром. Это не оформление: белый экран посреди тёмного двора
сбивает адаптацию глаза на двадцать минут, после чего слабые объекты просто
перестают быть видны. Ctrl+N, полный экран — F11.

## Фотографии участка

Архитектура готова к следующему этапу, но автоматической склейки пока нет.
Сейчас сохраняется привязка: путь к кадру, азимут центра, горизонтальное поле
и положение линии горизонта на кадре. Поддерживаются два режима — набор кадров
(`PHOTOS`) и готовая сферическая панорама (`EQUIRECTANGULAR`).

Импорт: «Участок → Импортировать фотографии». Кадрам проставляются равномерные
азимуты, которые нужно уточнить вручную.

## Хранение

`%APPDATA%\BinocularSky\settings.json` (переопределяется переменной
`BINOCULAR_SKY_HOME`). Хранятся площадки, приборы, участки, планы наблюдений и
настройки вида. В репозиторий это не попадает.

Запись атомарная: сначала временный файл, потом переименование. Битый или
отсутствующий файл не оставляет пользователя без профиля — подставляется набор
по умолчанию.

## Сборка под Windows

```
python scripts/build_binocular_sky.py
# или
.\scripts\build_binocular_sky.ps1
```

Результат: `dist/BinocularSky/BinocularSky.exe` (вариант «одна папка»).
Рядом с exe нужен каталог `data/` с эфемеридами и кэшем каталогов — так
обновление каталога не требует пересборки.

One-file собирается флагом `--onefile`, но не рекомендуется: Chromium из
QtWebEngine распаковывается во временный каталог при каждом запуске.

## Что это НЕ делает

Честный список ограничений первой версии:

* **Предельная величина — оценка.** Прозрачность атмосферы, влажность,
  адаптация и опыт наблюдателя не учитываются.
* **Блеск комет прогнозируется грубо** по формуле MPC `m = g + 5·lg Δ + k·lg r`;
  реальный блеск отличается на величины.
* **Астероиды в 3D-сцену не подключены** — только кометы и планеты.
* **Панорама по фотографиям не строится автоматически**: хранится привязка,
  склейки нет.
* **Звёздный каталог — Hipparcos до +6.5m** в сцене. Протокол уровней глубины
  (`star_levels`) готов под каталог до +11m, но такой каталог не подключён.
* **Погода и облачность не учитываются.**
* Затмения, покрытия и прочие события — это задача AstroCalendar Studio, здесь
  их нет.
